# AI Agent Verification Gate

## Purpose

This document defines the verification contract for the Proxmark5 engineering swarm. It is intentionally stricter than ordinary code review because repository evidence and physical-device evidence are different things.

## Non-negotiable rule

An agent may produce a claim, implementation or test result, but it may not promote its own output to a stronger evidence state.

```text
AGENT OUTPUT
    -> CONTRACT
    -> PROVENANCE
    -> SCOPE
    -> SAFETY
    -> INDEPENDENT REVIEW
    -> TEST / PROTOCOL / HOST / HARDWARE EVIDENCE
    -> PROMOTION
```

## Evidence promotion

Allowed states are:

```text
SOURCE / DOCUMENTED
STATIC ANALYSIS
UNIT TESTED
CI VERIFIED
PROTOCOL VERIFIED
HOST VERIFIED
REAL HARDWARE OBSERVED
HARDWARE VERIFIED
AUTOMATED IN CLIENT
```

Promotion requires evidence appropriate to the target state. CI can never promote a claim to hardware verification. A simulator can never promote a claim to hardware verification. An upstream PM3 implementation can never by itself promote a PM5 capability.

## Required agent result

Every result must identify:

- task ID;
- immutable repository SHA;
- agent role;
- exact scope;
- changed files;
- source/evidence references;
- current evidence state;
- requested evidence state, if any;
- tests executed and their environment;
- security/safety constraints;
- hardware requirement;
- unresolved assumptions;
- next handoff;
- blocker.

## Independent verification

The verifier must be a separate role/process from the implementation agent. At minimum it checks:

1. task SHA still matches the reviewed source;
2. changed paths are inside the declared scope;
3. every factual claim has provenance;
4. evidence state does not exceed available evidence;
5. dangerous hardware operations remain gated;
6. tests actually correspond to the changed contract;
7. no secret or credential is exposed;
8. documentation does not upgrade evidence labels without proof.

## Physical-device boundary

The following remain distinct:

- `SIMULATED` — generated by a simulator;
- `DETECTED` — observed by the application/device discovery path;
- `REPORTED` — reported by firmware or another source;
- `EXPECTED` — predicted from documentation or compatibility rules;
- `HYPOTHESIS` — unresolved technical assumption;
- `UNKNOWN` — insufficient evidence.

Only appropriate physical observations and repeatable verification procedures may establish hardware capability.

## Dangerous operations

AI automation must not silently flash, erase, downgrade, modify charger/power configuration, or otherwise perform irreversible/risky hardware operations. Such operations require exact device identity, compatibility checks, recovery planning and explicit human authorization.

## Failure handling

A verifier must return `BLOCKED` or `NEEDS-EVIDENCE` instead of guessing. A failed test does not become a successful result through wording changes. Conflicting evidence is retained and escalated to the Orchestrator.

## Automation boundary

GitHub Actions may enforce deterministic contract and evidence gates. An external AI runner may propose and implement changes on an isolated branch, but merge/release remains subject to the repository's protected verification gates and human authority.
