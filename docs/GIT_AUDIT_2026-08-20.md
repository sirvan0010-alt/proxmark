## 3. BWM protocol — PASS / PROTOCOL VERIFIED

- Request/response/broadcast framing exists.
- CRC scope is magic + command ID + length + payload.
- CRC provenance points to `RfidResearchGroup/Proxmark5_BWM_esp32` commit `b918166128e05455c2dcb4e232216d453bbf29ee`.
- A fixed CRC golden vector now protects against symmetric encode/decode regressions.
- Command definitions are preserved as an upstream snapshot.
- Stream parser tests cover fragmentation, multiple frames, garbage, bad CRC, invalid length and resynchronisation.

**Boundary:** this is protocol/source verification, not physical PM5 verification. Payload layouts remain below high confidence until evidence confirms them.

## 4. Read-only adapter — PASS

The adapter has an explicit allow-list containing only the five currently intended read-only BWM commands. Mutating commands are rejected before transport invocation. Cancellation remains observable rather than being swallowed as a generic transport error.

Tests cover malformed frames, mismatched command IDs, broadcast-vs-response confusion, transport failure, cancellation and the read-only policy.

## 5. Diagnostic model — PASS with clarified schema boundary

A deep audit found that the older `DIAGNOSTIC_SCHEMA.json` describes a planned hardware-oriented report shape while the implemented C# `DiagnosticReport` has a smaller runtime shape. That mismatch could have caused `pm5ctl export-schema` to export a schema that did not describe its own output.

This is now separated explicitly:

- `DIAGNOSTIC_RUNTIME_SCHEMA.json` = implemented runtime `DiagnosticReport` schema;
- `DIAGNOSTIC_SCHEMA.json` = planned hardware-oriented schema;
- `pm5ctl export-schema` = exports the runtime schema.

The hardware-oriented schema remains provisional until the first real PM5 session.

## 6. Compatibility / firmware policy — PASS

Hardware and firmware registries are intentionally separate. A dedicated `FirmwareCompatibilityRegistry` loader was added so `compatibility/firmware.json` is not incorrectly deserialized through the hardware registry model.

The intended sequence remains:

```text
Detect → identify family/revision → identify firmware
→ compare compatibility → explain result → offer established candidates
```

Unknown hardware identity must not produce a confident firmware recommendation. PM3/reference and PM5-specific sources remain explicitly separated.

## 7. Simulator — PASS / SIMULATED ONLY

The simulator remains clearly marked `SIMULATED_ONLY`. A new `BwmSimulatedTransport` exercises the real Core BWM framing and read-only adapter end-to-end without opening any physical transport. Its values are fixtures, not hardware evidence.

Simulator payload encoding is deterministic and explicitly little-endian where the fixture models a uint32. No fixture is promoted to hardware truth.
